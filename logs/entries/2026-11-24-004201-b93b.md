## 2026-11-24 — ci(M1): Setup Node 在自托管 runner 上不再用 GitHub npm 缓存 —— 每轮少下载 / 回传约 4 GB

### [E-2026-11-24-004201-b93b] ci(M1): Setup Node 在自托管 runner 上不再用 GitHub npm 缓存 —— 每轮少下载 / 回传约 4 GB

- type: ci
- scope: .github/workflows/verify.yml、.github/workflows/deploy.yml 的 actions/setup-node `cache`
- impact: Eden 的 PR 检查排队很久。查最近 4 轮 verify:Checkout 2–3 秒、npm ci 2–3 秒、npm run check 约 10 秒,但 Setup Node 要 265 / 280 / 850 / 411 秒,有一轮 Post Setup Node 还要 368 秒。日志显示 `cache: npm` 每轮从 GitHub 下载一份 4,235,249,962 字节的缓存(约 10 MB/s,中途会停住)再解压。原因是 M1 自托管 runner 的 npm 缓存目录是本机共用的 ~/.npm(2026-11-24 量到 10 GB,其中 _npx 2.5 GB 是各 MCP 工具的),setup-node 把整个目录当缓存来存和取,而 M1 本机本来就有这个目录。M1 上 Eden 只有一个 runner(m1-Eden),一轮 5–20 分钟,同一个 PR 连推几次后面就一直 Queued。改成和 personal-dashboard / LifeOs 一样:`cache: ${{ runner.environment == 'github-hosted' && 'npm' || '' }}`,只在 GitHub 托管机器上开(setup-node@v4 的 cache 为空时不开缓存;v5 才有的 package-manager-cache 这里不需要)。另外把仓库里 3 份旧 Actions 缓存(4.23 / 2.79 / 4.23 GB,接近每个仓库 10 GB 的上限)用 gh cache delete 删掉了。
- changed: .github/workflows/verify.yml, .github/workflows/deploy.yml
- ripples: M1 上 npm ci 直接读本机 ~/.npm;它坏了 Eden 的 CI 也会跟着异常(修法照全局规则:npm cache verify 或清空 ~/.npm)。CI_RUNS_ON 退回 ubuntu-latest 时会自动恢复 npm 缓存,不用改回来。deploy.yml 的 IndexNow 那一步本来就没开缓存，没动。
- learned: [rule] 仓库接到 M1 自托管 runner(设 CI_RUNS_ON)时,要把所有 workflow 里 setup-node 的 `cache: npm` 一起改成只在 github-hosted 时开;Eden 当初接上 M1 漏了这一步,每轮多花 5–15 分钟。[knowledge] 判断 CI「卡住」先看各步耗时(gh run view --json jobs 的 startedAt / completedAt),不要只看总时长;这次干活的部分只要 15 秒,其余全是缓存下载。
- verified: npm run check;PR 上的 verify 在 M1 跑,看 Setup Node 一步降到几秒、日志里没有 `Received … of 4235249962`
- keywords: CI, M1, self-hosted runner, actions/setup-node, cache npm, ~/.npm, Queued, 排队, Setup Node 慢, GitHub Actions cache
